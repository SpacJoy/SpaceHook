## 0. 先记住三句话

1. **这个 App 装上之后，平时你打开的那个界面（开关、设置）本身不干活。** 真正改系统行为的是被塞进「目标 App」进程里的那段代码。
2. **开关只是存了一个值，存在 LSPosed 的数据库里。** 两边的进程都去读同一个值，所以界面上的开关能影响另一个进程。
3. **改功能 = 改某个 Hook 文件；界面会自动跟着变。** 因为界面是照着 `HookCatalog` 里登记的信息画的，不用手写界面。

---

## 1. 这个项目是做什么的

一个 LSPosed 模块（也可以叫 Xposed 模块）。它的作用是：

**把「针对不同 App 的小改动」集中到一个 App 里管理。**

比如「锁屏时钟显示冒号」「抖音视频不裁剪」「录音列表点了不自动播放」，本来是三个互不相关的小工具，现在合并进一个 App，用开关分别控制。

它和普通 App 最大的区别：

| | 普通 App | 这个模块 |
|---|---|---|
| 代码在哪运行 | 自己进程里 | 自己进程 + 被选中 App 的进程里 |
| 怎么起作用 | 自己画界面、自己算 | 改别人 App 里的方法，让它表现不一样 |
| 装完就完事 | 是 | 不是，装完还要在 LSPosed 里勾选作用域 |

「Hook」这个词的意思就是：**在别人的代码跑到某个方法时插一脚**，可以看参数、改参数、改返回值、或者干脆不让它执行。

## 2. 三个文件夹（模块）分别是干什么的

项目根目录下有三个源码文件夹，一个 APK 装出来是合在一起的：

```
Xposed.spacejoy.top/
├── common/     公共数据：功能清单、开关的名字、各种常量
├── libhook/    真正干活的代码：每个功能的具体实现
└── app/        界面：开关页、设置页、首页
```

### common —— 只放「数据和名字」，不放逻辑

| 文件 | 里面是什么 |
|---|---|
| `HookCatalog.kt` | **功能总清单**。有哪些目标 App、有哪些功能、每个功能叫什么名字、说明文字、默认开不开、有哪些可调参数。界面上显示的东西全部来自这里 |
| `HookMeta.kt` | 上面那个清单里每一条的「格式」（有哪些字段） |
| `HookPrefs.kt` | **所有开关的名字**（键名）。比如总开关叫 `global_master_enable`，某个功能开关叫 `hook::lock_colon` |
| `Constants.kt` | 各种固定值：包名、日志目录、远程配置的组名等 |

**这个模块有一条硬性规定：不许引用 libxposed 和 Compose。**
原因：这个模块的代码会被界面进程加载。libxposed 的代码在界面进程里根本不存在（它由框架在运行时提供），一旦引用，界面一打开就崩。

### libhook —— 真正改别人 App 的地方

| 文件 | 干什么的 |
|---|---|
| `SpaceHookEntry.kt` | **入口**。框架加载模块时第一个跑这里。负责「这是哪个进程 → 该加载哪些功能 → 一个个装上去」 |
| `base/BaseHook.kt` | **工具基类**。把「找类、找方法、挂钩子」这些重复操作包好了，写新功能时直接调 |
| `base/HookRegistry.kt` | **id → 实现类** 的对照表。功能清单里写了 `lock_colon`，这里说明它对应哪个类 |
| `base/HookContext.kt` | 运行时信息（当前是哪个包、哪个进程、类加载器） |
| `utils/PrefsBridge.kt` | **读开关**。判断「这个功能该不该加载」的全部逻辑在这里 |
| `utils/XLog.kt` | 打日志 |
| `utils/ClassLoaderUtils.kt` | 在 SystemUI 里找插件的类加载器（只有 MIUI 场景需要） |
| `rules/` | **每个功能一个文件**，按目标 App 分文件夹。要改某个功能的行为，就是改这里的文件 |

### app —— 界面

| 文件 | 干什么的 |
|---|---|
| `MainActivity.kt` / `SpaceHookApp.kt` | 程序入口，做初始化 |
| `SettingsStore.kt` | **读写设置**。界面上的开关点一下，存到这里 |
| `xposed/XposedServiceManager.kt` | 和 LSPosed 框架对话：判断模块激活没有、拿框架版本、拿「正在运行的生效进程」列表 |
| `ui/SpaceHookNavHost.kt` | 页面跳转规则（哪个页面跳到哪个页面、动画怎么走） |
| `ui/MainScreen.kt` | 一级外壳：顶部标题栏 + 底部三个页签 |
| `ui/screens/HomeScreen.kt` | 首页 |
| `ui/screens/HookListScreen.kt` | 功能列表页（最长的文件，1400 行） |
| `ui/screens/HookParamsScreen.kt` | 功能参数页（点某个功能进去调数值的地方） |
| `ui/screens/SettingsScreen.kt` | 设置页 |
| `ui/theme/SpaceHookTheme.kt` | 主题、颜色、字号 |

## 3. 一个开关，从「点下去」到「真的生效」，走的路

这是整个项目最值得搞清楚的一件事。以「锁屏大时钟显示冒号」为例：

```
① 你在功能列表页，点了一下那个开关
      ↓
② HookListScreen 调用 SettingsStore.setHookEnabled("lock_colon", true)
      ↓
③ SettingsStore 把值写进 —— 注意，不写在自己 App 的存储里
   而是通过 XposedServiceManager 拿到的「远程存储」
      ↓
④ 这个「远程存储」实际是 LSPosed 自己的数据库，组名 spacehook_config
      ↓
⑤ 系统界面进程（com.android.systemui）重启时，LSPosed 把模块塞进去
      ↓
⑥ SpaceHookEntry.onModuleLoaded 跑起来，用同一个组名拿到同一份存储
   → 放进 PrefsBridge
      ↓
⑦ LSPosed 通知「这个包准备好了」→ SpaceHookEntry.onPackageReady
      ↓
⑧ dispatch() 干活：
   a. 这个包已经分发过了吗？（防重复）
   b. 总开关开了吗？安全模式开了吗？
   c. 从 HookCatalog 查：com.android.systemui 有哪些功能？→ 查到 lock_colon
   d. 这个功能的开关是开的吗？（Ada 四级判断）
   e. 从 HookRegistry 拿到实现类，new 一个出来
   f. 调它的 onHook()，在里面挂钩子
   g. 写一条「已生效」记录，给界面显示用
      ↓
⑨ 之后你每次锁屏，系统界面的那个方法被调用时，就会先走我们的代码
```

**关键理解**：第 ③ 步写的是一个「跨进程共享的存储」，不是普通 App 的本地存储。这就是为什么关掉再打开目标 App 能生效，而不用重启手机。

也是为什么「模块没激活时开关照样能点，但不生效」—— 那时写的是本地存储，另一个进程读不到。

### 开与关的四道闸门

一个功能要不要加载，按顺序过四关，任何一关不过就跳过（代码在 `PrefsBridge.isHookEnabled`）：

| 顺序 | 判断什么 | 对应键名 |
|---|---|---|
| 1 | 全局总开关 | `global_master_enable` |
| 2 | 安全模式（暂停一切） | `global_safe_mode` |
| 3 | 这个 App 的总开关 | `app_master::包名` |
| 4 | 这个功能自己的开关 | `hook::功能id` |

界面上：功能列表页里，每个 App 卡片头部的那个开关 = 第 3 关；展开后每个功能旁边的开关 = 第 4 关。

## 4. 哪些是「框架要求这么写」，哪些是「自己写的」

分清这个，你才知道哪些不能乱动。

### 框架要求的（改了就坏，照抄即可）

| 东西 | 位置 | 为什么必须这样 |
|---|---|---|
| 入口类名 | `libhook/src/main/resources/META-INF/xposed/java_init.list` | 框架靠这个文件找到入口。里面只有一行类名 |
| 模块声明 | 同目录 `module.prop` | 声明支持哪个 API 版本、作用域是否固定 |
| 作用域清单 | 同目录 `scope.list` | 一行一个包名。**新增目标 App 必须加这里**，否则框架不会把模块塞进去 |
| 三个回调方法的名字 | `SpaceHookEntry.kt` | `onModuleLoaded` / `onPackageReady` / `onSystemServerStarting` 是框架固定调用的名字 |
| 出口类的继承 | `SpaceHookEntry : XposedModule()` | 必须是这个基类的子类 |
| 混淆保护规则 | `libhook/proguard-rules.pro` | 打正式包时防止入口类被改名 |

### 自己写的（随便改，改完界面自动适配）

| 东西 | 位置 |
|---|---|
| 有哪些功能、叫什么、说明文字 | `common/HookCatalog.kt` |
| 每个功能具体怎么改对方的代码 | `libhook/rules/各功能.kt` |
| 界面长什么样 | `app/ui/` 下面 |
| 开关怎么判断 | `libhook/utils/PrefsBridge.kt` |
| 键名怎么起 | `common/HookPrefs.kt` |

### 关于 API 102 的钩子写法（和网上老教程不一样）

网上搜到的 Xposed 教程大多讲的是老 API，用 `XposedHelpers.findAndHookMethod`、`param.setResult(...)`。
**这个项目用的 API 102 完全不是那套**，是「拦截器链」写法：

```kotlin
module.hook(方法)
    .intercept { chain ->
        chain.args[0] = "改个参数"   // 改参数
        chain.proceed()              // 继续执行原方法
        // 直接 return 某个值 = 不让原方法执行，直接返回这个值
    }
```

- **没有** `setResult()` / `getResult()`
- 拦截块「最后返回什么」，就是那个方法的返回值
- 忘了写 `chain.proceed()` 就等于把原方法干掉了（有时候是故意的，有时候是 bug）

不过这个项目已经把它包进了 `BaseHook`，写新功能时用这几个现成方法就行：

| 方法 | 用途 |
|---|---|
| `before(类, "方法名") { }` | 在原方法执行前做点事，之后照常执行 |
| `replace(类, "方法名") { }` | 接管这个方法，返回什么就是什么 |
| `hookAllMethods(类, "方法名") { }` | 同名方法有多个（重载）时全部挂上 |
| `hookConstructor(类)` | 拦构造方法 |
| `findClass("类名")` | 找类，找不到返回 null（安静跳过，不崩） |
| `setField(对象, "字段名", 值)` | 改对象的字段（常用于钉死某个开关变量） |
| `callMethod(对象, "方法名", 参数)` | 调用对象的方法 |

### 加一个新功能的完整流程

1. 用 jadx 反编译目标 App，找到「哪个类的哪个方法」是要下手的地方（详见 `AGENTS.md` 第 6 节）
2. `HookCatalog.kt`：目标 App 没登记先加 `targetApps`，再加 `HookMeta`
3. 新建 `libhook/rules/<分类>/XxxHook.kt`，继承 `BaseHook`，在 `onHook()` 里挂钩子
4. `HookRegistry.kt`：把 id 和这个类对上
5. 目标 App 是新的 → 往 `scope.list` 加包名
6. 补文档：`docs/HOOKS.md` 加一节，`docs/PROGRESS.md` 记一笔

**注意：界面不用改。** 它是照着 `HookCatalog` 画的。

## 6. 出问题时，按这个顺序查

### 第一步永远是这个（重要）

看 LSPosed 的日志里有没有这一行：

```
SpaceHook 已注入：process=xxx, framework=...
```

**搜不到就是没被加载，这时候别改代码，重启手机。**
原因见下面「安全模式」那一段。这一步能避免大量无用功。

### 然后按日志往下看

在日志里搜关键词，每个关键词对应一个具体结论：

| 日志内容 | 说明什么 | 怎么办 |
|---|---|---|
| `SpaceHook 已注入` | 模块进这个进程了 | 正常，继续看下面 |
| `PrefsBridge 已接入，prefs=true` | 跨进程配置读到了 | `prefs=false` 说明存储没拿到，开关会退回默认值 |
| `没有匹配的 Hook（HookCatalog 中未登记该包名）` | 这个包压根没登记 | 去 `HookCatalog.kt` 加 |
| `匹配到 N 个 Hook：xxx` | 找到了 N 个功能 | 没有这行就是没登记或没被注入 |
| `xxx 已关闭，跳过` | 开关没开 | 界面上打开 |
| `Hook 装载成功 @ 包名` | 装上了 | 正常 |
| `目标类不存在，跳过：xxx` | **目标 App 更新了，类名变了** | 需要重新反编译定位，不是代码写错 |
| `方法不存在，跳过：类#方法` | 同上，方法名变了 | 同上 |
| `Hook 装载失败 @ 包名` + 异常 | 代码里有报错 | 看异常内容 |
| `分发完成：成功 N / 共 M` | 汇总 | N < M 就说明有失败的 |

### 关于「安全模式」这个坑（必须记住）

LSPosed 有个自我保护机制：如果某个进程崩溃了，它会把「那个进程里的所有模块」全停掉，防止一直崩。

**这个机制是按进程算的，不是按模块算的。**
也就是说：系统界面（com.android.systemui）崩了一次，**所有**在系统界面里生效的模块都会被跳过 —— 不只崩的那个。

而且**这个项目被跳过时一行日志都没有**（有的模块自己会打日志，所以日志里可能只看到别人的记录，更容易误判）。

所以：
- 「日志里完全没有 SpaceHook 的痕迹」本身就是安全模式的特征，**不要以为是代码没生效**
- 解除方式只有一个：**重启手机**
- 所以不要反复重启系统界面，改完代码优先用热重载（设置页 →「生效 → 立即热重载所有进程」）

### 怎么验证改动有没有生效

正常流程（覆盖安装就行，不需要卸载）：

```bash
# 1. 构建
/d/Code/Android/tools/gradle-9.3.1/bin/gradle --no-daemon :app:assembleDebug

# 2. 覆盖安装（-r 是覆盖，别卸载）
adb -s 192.168.31.5:5555 install -r -t app/build/outputs/apk/debug/app-debug.apk

# 3. 重启目标 App（改的是录音机就重启录音机，不要动不动重启系统界面）
adb -s 192.168.31.5:5555 shell am force-stop com.android.soundrecorder
```

覆盖安装会保留 LSPosed 里的「已启用」和作用域设置，不用重新勾。

## 8. 几个容易忘的概念

**包名（packageName）**
就是 `com.android.systemui` 这种唯一标识。整个项目到处用它来区分「是哪个 App」。装到手机上后不能改。

**进程 vs 应用**
一个 App 可能有多个进程（录音机有 `:remote` 子进程）。模块是按进程注入的，所以日志里会看到同一个包名出现多次。

**作用域（scope）**
「这个模块允许被塞进哪些 App」的白名单。写在 `scope.list` 里，但用户还能在 LSPosed 界面自己勾。**作用域为空时会应用到所有 App**，所以别让它空着。

**ClassLoader（类加载器）**
Android 每个 App 有一套自己的「类仓库」，模块要通过目标 App 的仓库去拿它的类。`BaseHook.findClass()` 已经处理了找仓库的逻辑。

**两类存储（容易搞混）**
| | 存在哪 | 谁能读 | 用来存什么 |
|---|---|---|---|
| 远程存储 | LSPosed 数据库，组名 `spacehook_config` | 界面进程 + 被注入的进程 | 所有开关、功能参数、「已生效」记录 |
| 本地存储 | 模块 App 自己的文件，名 `spacehook_local` | 只有界面进程 | 主题、字号、「见过哪些进程」这种纯界面用的东西 |

判断当前用的是哪个：`SettingsStore.isRemote`。界面在未激活时会提示。

**热重载**
API 102 的功能：不用重启目标 App，直接让新装的模块代码在已运行的进程里重新加载。设置页有按钮。**改完代码优先用它，别用 killall 系统界面。**

## 9. 别动的东西（清单）

- `libhook/src/main/resources/META-INF/xposed/` 下三个文件的内容格式（`module.prop` / `java_init.list` / `scope.list`）—— 格式错了模块直接不加载
- `HookCatalog` 里已经发布的 `id` —— 它同时是开关的键名，改了等于所有人的开关都失效
- `common` 模块里引入 libxposed 或 Compose —— 界面会崩
- `local.properties` —— 是本机的 SDK 路径，不要提交到 git
- `.workbuddy/` 目录 —— 是别的工具的工作记录，不是垃圾

## 10. 我（AI）改动之后，应该给出的说明格式

每次改完，用这三句话汇报，不要丢一堆代码过来：

1. **改了哪个文件**
2. **动了什么**（比如「把默认值从 8 改成 16」）
3. **为什么要改**（关联到哪个需求或哪个报错）
